# Meridian agent app

Cash-in / cash-out agent outlet app (installable offline PWA, English and Kiswahili) on http://localhost:13400. Same
stack as `web/meridian-console`: Next.js 16.4, React 19.3, Tailwind 4, openapi-fetch + React Query, oidc-client-ts.

```bash
npm install
npm run gen:api      # typed client from generated/openapi/services/agent-channel-service.openapi.yaml (src/api/agent-channel.d.ts)
npm run dev          # http://localhost:13400 (/v1/* proxied to MERIDIAN_GATEWAY_URL, default http://localhost:18000)
npm run typecheck    # next typegen && tsc
npm test             # vitest: outbox (ordering, idempotency keys, reconciliation, encryption, limits) + device-key payloads
npm run build
npm run test:e2e     # Playwright smoke against the build with the API mocked (offline capture, device proof, PWA shell)
```

## Identity

Sign-in: OIDC (Keycloak realm `meridian`, code + PKCE, client `NEXT_PUBLIC_OIDC_CLIENT_ID`, default
`meridian-agent-app`, generated by `tools/keycloak_realm.py`): scope `channels:agent` only, `agent_id` / `tenant_id`
claims from admin-managed user attributes (the user cannot change them), `auth_time` / `acr`. Local demo user:
`demo.agent` / `Meridian#Agent2026`; set its `agent_id` attribute (Keycloak admin, Users -> demo.agent -> Attributes)
to an ACTIVE agent of tenant `0199a000-0000-7000-8000-00000000000a`. Dev mode (`/login`): tenant, user and agent id;
requests carry `X-Tenant-Id`, `X-User`, `X-Agent-Id` and the sign-in time as `X-Auth-Time` (honoured only by services in
dev security mode).

The agent is never chosen in the app: setup reads it from `/v1/agent/me`, the agent picks one of its outlets, the
device is registered with its signing key, and the 6-digit app PIN protecting the offline outbox is set.

## API

Every screen calls only the agent channel `/v1/agent/*` (`agent-channel-service`, client `api` in `src/api/client.ts`).
The server takes the agent from the token, answers 404 for any outlet, till, device, float / cash request, transaction,
receipt, bill payment, top-up, application, document or offline batch that is not the agent's, and rebuilds request
bodies itself (float wallet, currency, channel `AGENT_APP`, requesting agent, rebalance source, till operator, onboarding
channel and agent). The app sends only what the agent typed. Customer lookup returns masked data only
(`display_name_masked`, `msisdn_masked`, wallet id for cash-out) and is rate-limited per agent.

## Device binding

At setup `src/lib/device-key.ts` generates an ECDSA P-256 key pair with WebCrypto (`ES256`). The private key is created
non-extractable and kept as a `CryptoKey` in IndexedDB (`meridian-agent-keys`): the browser can sign with it but the key
cannot be read or copied. Only the public key (SubjectPublicKeyInfo, base64) is registered (`POST /v1/agent/devices`,
needs a recent sign-in). Settings shows the key and can register a fresh key (the server revokes the old one). The app
signs only while it is unlocked with the app PIN.

- Offline onboarding: the batch is signed at capture over the canonical text (tenant, agent, device, the outbox
  record's Idempotency-Key, capture window in epoch ms, application count, SHA-256 of `payload_uri`), stored signed in
  the encrypted outbox and replayed byte for byte (`POST /v1/agent/offline-batches`). The server verifies it with the
  registered key and refuses unknown devices (404), revoked keys and bad signatures (422).
- Money operations (cash-in, cash-out and its confirmation, bills, airtime, float requests) carry an
  `X-Agent-Device-Proof: v1.<device>.<epoch s>.<signature>` over (tenant, agent, device, method, path,
  Idempotency-Key, timestamp). The server accepts money movement with a sign-in at most 5 minutes old **or** a valid
  proof no older than 5 minutes, so the outbox can replay work captured offline without a new sign-in.

## Offline

The service worker serves the app shell and agent-channel reference data (billers, journeys, `/v1/agent/me`, outlets,
floats). Cash-in, bills, airtime, float requests and onboarding are captured into an outbox in IndexedDB encrypted with
AES-GCM under a key derived (PBKDF2) from the app PIN and bound to tenant + agent; the key and the agent's wallet PIN
live only in memory, customer PINs are never stored. Each operation gets its `Idempotency-Key` at capture and is
replayed in capture order. An unknown outcome is reconciled through the channel's `idempotency_key` lookups
(`/v1/agent/transactions`, `bill-payments`, `airtime-topups`, `float-requests`, `offline-batches`). Cash-out and
anything needing live verification is refused offline.

## Remaining gaps

- Larger offline batches: `payload_uri` is limited to 500 characters, so only one compact application fits inline per
  batch; an upload target for encrypted batch payloads (document-service) is needed.
- Ed25519 device keys are accepted by the server but the app uses ES256 (WebCrypto Ed25519 is not available on every
  agent device yet).
- No server-side check that a device proof was made after an app-PIN unlock (the PIN gate is enforced in the app only);
  platform attestation (Play Integrity / App Attest) would bind the key to genuine app installs.
- Typed quote and commission summary responses (both are `object` in the contracts); no gateway health endpoint (the
  connectivity probe uses `/v1/agent/billers`).
- Sub-agent management for super-agents is read-only (sub-agent list and KPIs); creating or suspending sub-agents stays
  with operators.
- A pending cash-out started by the customer is found by its reference among the agent's pending cash-outs (no
  reference filter on `/v1/agent/transactions`).
- Mid-shift till cash counts are not stored (only opening and closing counts).
