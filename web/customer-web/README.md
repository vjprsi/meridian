# Meridian customer web banking

Retail customer app (mobile first, installable PWA) on http://localhost:13300. Same stack as `web/meridian-console`:
Next.js 16.4 (Cache Components), React 19.3, Tailwind 4, openapi-fetch + React Query, oidc-client-ts.

```bash
npm install
npm run gen:api     # typed clients from generated/openapi/services -> src/api/gen (customer-channel, customer,
                    # onboarding-public = only /v1/onboarding/public/* of onboarding-service)
npm run dev         # http://localhost:13300 (/v1/* proxied to MERIDIAN_GATEWAY_URL, default http://localhost:18000)
npm run typecheck   # next typegen && tsc
npm run build
npm run test:e2e    # Playwright smoke against `npm run start`, mocked/absent backend, local Chrome (PW_CHANNEL=msedge)
```

Sign-in: OIDC (Keycloak realm `meridian`, code + PKCE, client `NEXT_PUBLIC_OIDC_CLIENT_ID`, default
`meridian-customer-web`, generated by `tools/keycloak_realm.py`: scope `channels:customer` only, `customer_id` /
`tenant_id` claims from admin-managed user attributes, `auth_time` / `acr` / `amr` / `sid`). The client's browser flow
has Levels of Authentication: acr 1 = password, acr 2 = password + a second factor (passkey, security key or
authenticator app). Local demo user: `demo.customer` / `Meridian#Customer2026` with a demo authenticator app (TOTP,
base32 secret `JVSXE2LENFQW4RDFNVXVI33UOAZDAMRW`, add it to any authenticator app); set its `customer_id` attribute
(Keycloak admin, Users -> demo.customer -> Attributes) to a customer of tenant `0199a000-0000-7000-8000-00000000000a`.
The client also allows the password grant for local scripts (pass `totp` too once the user has an authenticator app);
those tokens carry acr 1 and no `auth_time`, so the channel refuses step-up operations with them (use the code flow).
Dev mode: pick the tenant and a customer on `/login`; requests then carry `X-Tenant-Id`, `X-User`, `X-Customer-Id`,
`X-Session-Id` (random per sign-in) and, after a confirmation, `X-Auth-Time`, `X-Acr: 2`, `X-Amr: pwd,otp` (honoured
only by services in dev security mode). Every request carries `X-Device-Id`, a random id of this browser kept in
`localStorage` (not a secret; it lets the bank tell a new device from a known one).

API: every signed-in screen calls only the customer channel `/v1/me/*` (`customer-channel-service`, client `me` in
`src/api/client.ts`). The server takes the customer from the token, answers 404 for anything that is not theirs, builds
request bodies itself (customer, currency, creditor details, sender type...) and enforces step-up. The app sends no
customer ids and does no ownership filtering of its own (`src/api/me.ts`). The dev customer picker uses
customer-service (dev headers).

Sign-up (`/signup`, `src/api/applicant.ts`) needs no sign-in: it uses only the public applicant surface of
onboarding-service (`/v1/onboarding/public/applications/*`, typed client `src/api/gen/onboarding-public.d.ts`). The
tenant is `NEXT_PUBLIC_TENANT_ID` (unset: a local-development picker on the start screen) and the journey is the
tenant's published journey with code `NEXT_PUBLIC_SIGNUP_JOURNEY` (default `RETAIL_ONLINE`, also editable in the
picker). `start` returns the applicant token once; it is sent as `X-Applicant-Token`, kept in memory and
`sessionStorage` only (never `localStorage`), rotated with `token/refresh` 5 minutes before it expires (and before any
call made later than that), and dropped on submit (the server revokes it). Steps are rendered from next-step's typed
`fields` and validated client-side with the server's rules (`src/lib/step-fields.ts`); server `input.<field>` errors
are shown next to their fields. Phone / email steps use `otp/send` + `otp/verify` (resend cooldown from
`resend_after`, attempts left, lockout). Documents: `documents` (pre-signed upload) -> PUT -> `documents/{id}/complete`
with size and SHA-256. A 401/403 (token expired or revoked) or 409 `application_expired` ends the session with a
restart screen; a 429 disables the action for `Retry-After` seconds.

Routes: `/login`, `/signup` (public applicant flow: OTP, typed step forms, document upload, submit, status), `/` (accounts,
wallets, cards, loans, recent activity), `/accounts/[id]` (balance, transactions, statements, confirmation letter),
`/move` (history), `/move/transfer`, `/move/pay`, `/move/payees`, `/move/receipt/[id]`, `/standing-orders`, `/cards`,
`/cards/[id]` (freeze, channel controls, limits, report lost/stolen with replacement), `/loans`, `/loans/[id]`
(schedule, repayments, repay), `/insights` (spending by category, budgets, insight cards), `/rewards`, `/inbox`,
`/inbox/[id]`, `/profile` (details, contacts with OTP, addresses, notification preferences, registered devices),
`/security` (sign-in strength, second factors, sessions), `/kyc`, `/offline`.

Money movement: validate (`POST /v1/me/payments/validate`, body `{kind, from_account_id, to_account_id | payee_id,
amount, ...}`) -> review -> step-up -> `POST /v1/me/payments` with one Idempotency-Key per confirmation -> receipt (PDF
via `/v1/me/payments/{id}/receipt`). The server requires acr 2 from an authentication at most 5 minutes old for
payments, standing orders, loan repayment, payee add / trust, card unfreeze and limits, new contacts and device
revocation (per operation configurable), else 401 `step_up_required` with
`WWW-Authenticate: Bearer error="insufficient_user_authentication", acr_values="2", max_age=300` (RFC 9470).
`StepUpConfirm` steps up unless the token is acr 2 and younger than 4 minutes: OIDC popup
(`signinPopup({acr_values: "2", max_age: 300})`; Keycloak asks for the passkey / security key / app code, and the
password too when the sign-in is older than 5 minutes), dev mode an explicit confirmation. When the server still
answers `step_up_required`, the next confirmation steps up with exactly the challenge's `acr_values` / `max_age`.
A customer without a second factor (`GET /v1/me/security` `has_second_factor: false`) is sent to Security first.

Security (`/security`): current strength (acr, amr, last confirmation) and the step-up policy; second factors listed
from Keycloak through the channel; "Add a passkey / security key / authenticator app" and "Remove" leave for Keycloak
as application-initiated actions (`kc_action=webauthn-register-passwordless`, `webauthn-register`, `CONFIGURE_TOTP`,
`delete_credential:<id>`; Keycloak re-asks an existing factor first) and come back to `/security` with the outcome
(`kc_action_status`). Sessions (`/v1/me/sessions`): device, address, signed-in / last-seen, "This device" and
"New device" badges; sign out one session or everywhere (other devices only, or including this one, which also signs
out here). A request of a signed-out session gets 401 `session_revoked` and the app returns to the sign-in screen.

PWA: `app/manifest.ts` + `public/sw.js`. The worker caches only the app shell (`/_next/static`, icons, manifest,
`/offline`); `/v1/*`, `/auth/*` and credentialed requests bypass it, pages are network-only, and `/v1/*` responses
are served with `Cache-Control: no-store`. Session data lives in `sessionStorage` only.

Accessibility and i18n: WCAG 2.2 AA tokens for light and dark (system or chosen), visible focus, 44px targets, labelled
controls with described errors, skip link, landmarks, status text never colour-only. Messages in `src/messages/en.ts`
and `src/messages/sw.ts` (Kiswahili; the type requires every English key).

## API gaps (customer channel)

Closed: customer identity (`customer_id` claim, customer-only scope refused by every operator endpoint), the "me"
surface with object-level authorization on every reference (BOLA/IDOR), server-built bodies, inbox trust (sender /
opener / reader roles derived by inbox-service from the relayed customer; staff-only notes never returned),
server-side step-up (`auth_time` / `acr`) and the public sign-up surface (no staff endpoints or tenant principal),
customer MFA (Keycloak Levels of Authentication: passkeys, security keys, authenticator apps; acr 2 step-up with
RFC 9470 challenges; optional amr per operation) and customer sessions (`/v1/me/sessions`, sign out everywhere,
new-device alerts). Still open:

1. **MFA follow-ups.** The first second factor is enrolled with the password only (Keycloak AIA at acr 1): enrol it
   at onboarding (verified phone) or add a cooling-off for high-risk operations after a new factor; no SMS OTP factor
   (Keycloak has no built-in SMS authenticator); no recovery codes (disabled in the realm); factor changes are not yet
   alerted (Keycloak events are not forwarded to notification-service). `GET /v1/me/security` is untyped (`object`).
2. **Untyped responses** (`type: object` in the contract): `myPaymentsValidate`, `myInsightsSpending`,
   `myDocumentsUploadUrl`, and on the applicant surface `onboardingApplicantDocuments` /
   `onboardingApplicantDocumentsComplete` and the step `fields` items (shapes in `src/api/types.ts`). The
   `X-Applicant-Token` header is not declared as a parameter of the public operations.
3. **Sign-up details.** There is no public journey listing (the journey code is configuration), the attestation /
   CAPTCHA check is a server placeholder (the app sends no `attestation_token`), the services send no `Retry-After`
   on 429 (the app falls back to the time in `otp_resend_too_soon` or a generic "wait" message), and after submit the
   applicant cannot read the decision (the token is revoked; the outcome is communicated by the bank).
4. **Transactions are raw ledger entries** (`myAccountsTransactions`): no counterparty, merchant or category for a
   customer-friendly feed; enrichment (`transactionEnrichments*`) is a separate lookup per entry.
5. **Joint-account activity.** `/v1/me/payments` lists the customer's own payments; payments a co-holder made from a
   joint account appear only as account entries.
6. Tracker screens not built yet: passwordless passkey sign-in as the first factor (passkeys are a second factor
   today), tax certificates, open-banking consents, P2P/wallet transfers, bill payments, card PIN and PAN reveal.
