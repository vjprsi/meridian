# Multi-region cells, disaster recovery and deployment models (S20)

Exit criterion of roadmap step S20: **region failover RTO < 5 minutes and RPO 0 in a game day.** This document is the
design and the runbook. It also says plainly where RPO 0 holds and where it does not.

Pieces in the repository:

| Piece | Where |
|---|---|
| Cell registry, DR standby, routing view, tenant moves (maker-checker) | `spec/domains/platform.yaml` (tenant-service: `cell`, `tenant`, `tenant_placement`, `tenant_move`), `services/tenant-service` |
| Cell router | `platform/cell-router` |
| Cell identity in the cell chart, router chart | `infra/helm/meridian` (`global.cell.*`), `infra/helm/meridian-router` (both generated by `tools/helm_chart.py`) |
| One cell on AWS | `infra/tofu/modules/cell` |
| Region pair (two cells, Aurora Global Database, MSK Replicator, S3 CRR, Route 53 failover) | `infra/tofu/modules/region`, example `infra/tofu/envs/prod-eu1` |
| Data mover for tenant moves (MR-GAME-DAY) | `platform/data-mover`, move API in `libs/meridian-web` (`DataLifecycleService.move*`), Helm `dataMover.*` in the router chart |
| Standby promotion without restart, outbox replay retention | `libs/meridian-events` (`CellRole`, `StandbyGate`, `OutboxReplay`, `OutboxRetention`), `libs/meridian-web/.../ops` (operator switches, registry watcher) |
| Game-day kit: RPO probe, fault injection, FIS templates, dashboard | `tools/gameday`, `infra/observability` (`meridian-gameday` dashboard) |

## 1. Topology

```
                 Route 53  api.eu.meridian.example  (failover records, HTTPS health checks on /healthz)
                    |  PRIMARY                          |  SECONDARY
           +--------v---------+               +---------v--------+
           | cell router x3   |  eu-west-1    | cell router x3   |  eu-west-2
           +--------+---------+               +---------+--------+
                    |   tenant -> home cell (standby cell when the home cell is OFFLINE)
       +------------+-------------+                     |
       v                          v                     v
 cell euw1c01 (ACTIVE)      cell euw1c02 (ACTIVE)   cell euw2c01 (READ_ONLY warm standby of euw1c01)
 EKS + Aurora writer        ...                     EKS + Aurora Global secondary (read-only)
 MSK  --- MSK Replicator --------------------------> MSK (identical topic names, consumer offsets)
 S3 documents <------------- S3 CRR both ways ------> S3 documents
```

- A **cell** is a full Meridian stack (all services, edge gateway, its own Aurora cluster, MSK cluster, S3 bucket, KMS
  key) in one region, spread over three AZs. Tenants live in exactly one home cell.
- The **tenant registry** (tenant-service, control plane) knows the cells (region, status, capacity, deployment model,
  gateway URL, paired standby) and every tenant's home cell, standby cell, traffic mode and placement history. All of it
  is platform-operator only (SEC-15: scope `platform:operator`, operator tenant or internal service token).
- The **cell router** is the regional front door. It is stateless: tenant -> cell comes from the registry, cached.

### Why a separate cell router (not an edge-gateway mode)

The edge gateway is per cell and maps paths to services; the router sits above the cells and maps tenants to cells.
Keeping them apart means: the router has a tiny dependency surface (no route-to-service table, no service
credentials), scales and deploys independently of any cell, survives the loss of any one cell (including the one
hosting the control plane, thanks to stale-if-error caching and break-glass overrides), and a bad cell release cannot
take the region's front door with it. Both apply the same header policy (SEC-13 / SEC-16); `HeaderPolicyParityTest`
fails if they drift.

## 2. Cell registry and placement

Cell (`/v1/platform/cells`): `code`, `region`, `country`, `deployment_model` (`SHARED` / `DEDICATED` / `SELF_HOSTED`;
dedicated and self-hosted cells hold one tenant), `capacity_tenants`, `tenant_count`, `gateway_url`, `health_url`,
`endpoints`, `standby_cell_id` (default DR pair), `status`:

| Status | Router behaviour | How |
|---|---|---|
| PROVISIONING | routed (setup traffic) | create |
| ACTIVE | routed | create, PATCH from PROVISIONING / DRAINING, `/online` |
| DRAINING | routed, no new tenants | `/drain` |
| READ_ONLY | reads routed, writes 503 `cell_read_only` | `/read-only` (warm standby, maintenance) |
| OFFLINE | tenants go to their standby cell | `/offline` (break-glass, single operator, audited) |
| DECOMMISSIONED | not routed | PATCH, only when empty |

Every serving-state change publishes `platform.cell.status_changed` (the router applies the row at once).

Tenant: home cell (`cell_id`), `standby_cell_id` (`/set-standby`; else the home cell's paired standby), `traffic_mode`
(`NORMAL`, `READ_ONLY` while a move freezes writes, `BLOCKED`), `active_move_id`. Placement history
(`/placements`) records PRIMARY and STANDBY placements with the move that created them. Rules
(`io.meridian.tenant.domain.Placement`): a move target is another ACTIVE cell with room; a standby is another cell
that is ACTIVE or READ_ONLY; data residency uses the cell's `country` (else the tenant's home region); the router
view drops a paired standby that would break residency.

`GET /v1/platform/tenants/{id}/routing` is what the router reads: tenant status, traffic mode, home and standby cell
(status, gateway URL).

### Moving a live tenant (maker-checker)

`/v1/platform/tenants/{id}/migrate` is now only for PROVISIONING tenants (no data yet). A tenant with data moves through
`/v1/platform/tenant-moves`:

1. **Plan** (maker, `POST /tenant-moves`): validates target, capacity, residency, one open move per tenant; opens a
   `tenant_move` approval request in workflow-service (owner tenant-service). Status `PENDING_APPROVAL`.
2. **Approve** (checker, in workflow-service): four-eyes enforced when the decision is executed; rejected / expired /
   cancelled decisions end the move (`REJECTED`) and release the tenant.
3. **Freeze** (`/freeze`): tenant `traffic_mode = READ_ONLY`; the router answers writes with 503 + `Retry-After`,
   reads keep flowing from the source cell. Event `platform.tenant.traffic_mode_changed` invalidates router caches.
4. **Copy hand-off** (`/start-copy`): event `platform.tenant_move.copy_requested` carries source and target cells
   (gateway, database and Kafka cluster ids), strategy (`LOGICAL_REPLICATION`, `DUMP_RESTORE`, `NONE` when both cells
   share a database cluster) and `not_before_checkpoint`, plus each cell's `endpoints` (services URL template, document
   bucket). The data mover (`platform/data-mover`, [section 8.1](#81-data-mover)) copies the tenant's rows from every
   service database (RLS tenant column) and the tenant's documents.
5. **Confirm** (`/confirm-copy`, data mover): checkpoint (`mover:v1 rows=<n> tables=<t> docs=<d> sha256=<manifest
   digest>`: per-table row counts and content checksums, the full manifest stays in the mover database) and
   `verified=true`. Refused before `frozen_at + meridian.tenant.move.freeze-grace` (45 s = router cache TTL + request
   timeout), so a write admitted by a router that had not yet seen the freeze cannot land after the checkpoint.
6. **Switch** (`/switch`): capacity moves, the PRIMARY placement switches (`platform.tenant.migrated`); reads follow at
   once, writes stay frozen.
7. **Unfreeze** (`/unfreeze`): traffic mode NORMAL on the target; `COMPLETED`.

`/cancel` works until the switch and unfreezes the tenant on its source cell. Every step is in `history`
(`step, status, at, by, detail`) and published as `platform.tenant_move.*`.

## 3. Cell router

Per request:

1. **Tenant**: jwt mode - the `tenant_id` claim of a bearer token verified against the IdP JWKS (signature, issuer,
   expiry, audience SEC-14). `X-Tenant-Id` and the other internal headers are never read and are stripped (SEC-13).
   Public provider callbacks (routes marked public in the contract) without a token: the `tenant_id` query parameter
   (the cell still verifies the provider signature, SEC-17). dev mode (local only): `X-Tenant-Id`.
2. **Placement**: cache per tenant (TTL 30 s, negative TTL 5 s, single-flight lookups), dropped at once by
   `platform.tenant.*` / `platform.tenant_move.*` events; cell rows from `platform.cell.*` events and a full refresh
   every 15 s. While the registry is unreachable, cached placements keep serving for up to 15 min (stale-if-error).
   Every router instance reads every event (own consumer group, latest offset) and clears its cache after a
   partition reassignment.
3. **Decision** (`RoutingPolicy`): BLOCKED -> 503; READ_ONLY tenant -> writes 503 (`tenant_read_only`, Retry-After),
   reads routed; home cell OFFLINE (or, with `health.auto-failover`, failing health checks) -> standby cell if it is up,
   else 503 `cell_unavailable`; target cell READ_ONLY -> reads only.
4. **Proxy**: streams to `<gateway_url><path>`, same header policy as the edge gateway, body cap, `X-Meridian-Cell`.

Health checks probe each cell gateway every 5 s with hysteresis (unhealthy after 3 consecutive failures, healthy again
after 5 consecutive successes). They only trigger failover with `auto-failover: true`, which is safe where standby cells
are READ_ONLY warm standbys: an automatic failover then serves reads and never sends writes to an unpromoted database.
Otherwise failover is an operator decision (`/offline`).

Break-glass: `meridian.router.cell-overrides` (Helm `router.cellOverrides`, e.g. `{euw1c01: OFFLINE}`) wins over the
registry, for a regional failure that also took the control plane down.

Metrics (management port, not the routed port): `meridian.router.requests{cell,outcome}`,
`meridian.router.upstream{cell,outcome}` (latency), `meridian.router.failover.requests{from_cell,to_cell}`,
`meridian.router.cell.healthy{cell}`, `meridian.router.cell.serving{cell}`,
`meridian.router.placement.lookups{result=hit|miss|stale}`, `meridian.router.placement.invalidations`.

The router reads the registry with its own Keycloak client `meridian-cell-router` (client credentials, scope
`platform:routing-read` only, tokens carry the platform-operator tenant; no `meridian:internal`, no
`platform:operator`). `GET /v1/platform/tenants/{id}/routing`, `GET /v1/platform/cells` and `GET /v1/platform/cells/{id}`
declare `x-required-scope: platform:routing-read` (spec `scopes:`; `platform:operator` still accepted); the scope is
never implied by `platform:*` or `meridian:admin` and is honoured only for the operator tenant or internal tokens.
Helm: `router.auth.clientSecret` (default `meridian-cell-router-client`), `router.auth.scope` `platform:routing-read`.
The router never forwards a caller's token to the registry.

## 4. Data replication and RPO

| Failure | Database | Events | Documents | RPO |
|---|---|---|---|---|
| Pod / node | Aurora (writer elsewhere) | Kafka RF 3, `acks=all`, idempotent producer | S3 | 0 |
| AZ loss | Aurora storage: 6 copies over 3 AZs, a commit is durable at a 4/6 quorum; reader promoted (~30 s) | MSK across 3 AZs, `min.insync.replicas=2` | S3 multi-AZ | **0** |
| Region, **planned** (game day, region evacuation) | Aurora Global **switchover** (managed planned failover): waits until the secondary has every committed transaction, then swaps roles | drain: stop the relay, wait for MSK Replicator lag 0, then switch | S3 CRR (RTC 15 min SLA, typically seconds); verify `ReplicationLatency` = 0 / pending ops 0 | **0** |
| Region, **unplanned** | Aurora Global **failover** (`--allow-data-loss`): the secondary is promoted at its last applied position | MSK Replicator is asynchronous | CRR asynchronous | = replication lag at the failure: typically < 1 s, bounded by `rds.global_db_rpo` (20 s minimum) |

Honest statement: **with managed AWS services RPO 0 holds for AZ failures and for planned regional failovers; an
unplanned loss of a whole region loses the replication lag (sub-second in normal operation).** Aurora Global, MSK
Replicator and S3 CRR are all asynchronous across regions; no managed AWS database offers synchronous cross-region
commit. Options if the regulator or the tenant requires RPO 0 for unplanned regional loss:

1. **Synchronous ledger replication**: run `ledger_db` (only) on PostgreSQL with a synchronous standby in the second
   region (`synchronous_standby_names = 'ANY 1 (...)'`, `synchronous_commit = remote_apply`), self-managed or on a
   distributed SQL engine with a three-region quorum. Cost: one inter-region round trip per commit (eu-west-1 <->
   eu-west-2 is ~10-12 ms); the ledger G1 benchmark (1,792 postings/s, `docs/PERFORMANCE.md`) is latency-bound per
   posting and must be re-run.
2. **Reconcile the window**: every money movement is idempotent and has an external counterpart (card network advice,
   rail messages, statement files). After an unplanned failover, reconciliation-service replays counterpart files for
   `[failover - lag, failover]`; customers' retried requests replay by Idempotency-Key. This bounds the business impact
   of the lost window but is not RPO 0.

The game day therefore measures RPO 0 on the **planned** regional failover and on an AZ failure, and records the
measured lag (target < 1 s) for the simulated unplanned failover.

Events across the failover: the transactional outbox lives in each service database, so an event committed with its
business change is replicated with it. Rows not yet relayed are relayed by the promoted region. Rows already relayed
in the old region but not yet copied by MSK Replicator are the event-side gap of an unplanned failover. Relayed rows
are now **kept for a retention window** (`outbox.published_at`, `meridian.events.retention.window`, Helm
`global.outbox.retention`, default 72 h; purged in batches afterwards), so the promoted region re-publishes them with
their **original CloudEvent ids** and closes that gap: automatically on promotion
(`global.cell.promotion.replayOnPromote`, default 60 s before the newest replicated `published_at`, once per row), or
by an operator (`POST /v1/internal/ops/outbox/replay`, [section 8.3](#83-outbox-replay-retention)).

Is a replay safe? Every Kafka consumer was checked (MR-GAME-DAY):

| Consumer | Replay with the original `ce_id` |
|---|---|
| audit-service `DomainEventAuditListener` | safe: unique `(tenant_id, source_event_id)` |
| webhook-service `DomainEventConsumer` | safe: per (endpoint, event id) |
| search-service indexer | safe: upsert with `source_version` check (older snapshots ignored) |
| commission `WalletEventsListener`, rewards `CardEventsConsumer`, payment `FraudAlertListener` | safe: one effect per source entity / state machine |
| approvals dispatcher (libs/meridian-approvals, every service) | safe: handlers act only on resources still waiting (contract of `ApprovalOutcomeHandler`) |
| fraud `ModelEventsListener` | safe: cache reload only |
| crm `TimelineProjector` | safe in practice: check-then-insert on `ce_id` (no unique index: concurrent consumers could race) |
| notification `DomainEventListener` | **partial**: dedupe on (ce_id, channel, recipient, destination) without a unique index; a replay after the customer changed preferences / contact can send again |
| fraud `FeatureEventsListener` | safe within 8 days (event-id dedupe table pruned after `EVENT_RETENTION`); older replays bump profile aggregates again |
| collections `DelinquencyListener` | **not safe for out-of-date events**: no version / time check, an old DPD>0 event can reopen a cured case |
| cell-router `RegistryEvents` | cell rows applied without a version check: an old OFFLINE row flips routing until the next 15 s refresh |

Replays inside the default windows (60 s on promotion, an operator range of minutes) are therefore safe for money
movement; the four weaker consumers are follow-ups (section 7) and an operator replay should filter event types
(`event_types`) when it reaches back further.

Warm standby cells run every service at minimum replicas with `global.cell.role: standby`: the outbox relay is paused
and every Kafka listener is held (the topics are replicated, consuming them would apply events twice), the database is
read-only. **Promotion happens in place, without a rolling restart** ([section 8.2](#82-standby-promotion-without-restart)).

Secrets: the primary cell's database secrets are replicated to the standby region (same users as the replicated
database). KMS keys are per region; S3 CRR re-encrypts with the destination key.

## 5. Failover runbook (game day)

Roles: incident commander (IC), platform operator A (maker / executor), operator B (checker where needed), scribe
(timestamps). Pre-checks the day before: replication lag alarms green, standby cell READ_ONLY and healthy in the router
metrics, standby services at min replicas and ready, Route 53 health checks green for both routers, a synthetic
tenant on the primary cell with a continuous write/read probe (records the last acknowledged write id).

### Unplanned (simulated region loss)

| T+ | Step | Command / signal | Budget |
|---|---|---|---|
| 0 | Fault injected (block the primary cell's gateways and database at the network layer) | AWS FIS `tools/gameday/fis/region-loss.json` / security-group deny | |
| 0-60 s | Detection: router health checks (3 x 5 s), cell gateway readiness, Aurora lag alarm; IC declares failover | `meridian.router.cell.healthy{cell=euw1c01} = 0` | 60 s |
| 60 s | Reads move: operator marks the home cell OFFLINE; tenants' reads go to the READ_ONLY standby (writes get 503 + Retry-After) | `POST /v1/platform/cells/{euw1c01}/offline {"reason":"game day"}`; if the control plane is down: router `cellOverrides` | 15 s |
| 60 s | Database: promote the secondary | `aws rds failover-global-cluster --global-cluster-identifier meridian-eu1 --target-db-cluster-identifier <euw2 arn> --allow-data-loss` | 60-120 s |
| ~180 s | Writes move: standby cell online | `POST /v1/platform/cells/{euw2c01}/online` (router applies the event in < 1 s, refresh 15 s worst case) | 15 s |
| ~180 s (automatic) | Standby services promote in place: each sees its cell ACTIVE in the registry (poll 5 s), waits until the database accepts writes, replays the last 60 s of relayed events, resumes the relay, starts its listeners. No pod restarts. Manual path / status: `python tools/gameday/faults.py promote-cell` / `cell-role` | `meridian_outbox_relay_paused` drops to 0 per service | 5-10 s after the DB step |
| ~200 s | Verify: probe tenant writes succeed on euw2c01 (`tools/gameday/rpo_probe.py`), `failover.requests` rising, error rate back to baseline | `Meridian / Game day` dashboard | 30 s |
| < 300 s | **RTO met** (no rolling restart on the critical path) | | margin ~90-100 s |

RTO impact of in-place promotion: the previous step was a `helm upgrade --set global.cell.role=primary`, i.e. a rolling
restart of ~65 services at minimum replicas (JVM start + Flyway check + readiness ~60-90 s per pod, maxUnavailable 0),
budgeted at 90-120 s and overlapping the database step. Promotion now costs the registry poll interval plus the
database wait, a few seconds after Aurora reports the secondary writable, and frees ~60-90 s of RTO margin; pods keep
their warm JIT and connection pools. A `helm upgrade` to `role: primary` afterwards only makes the role permanent
(and is a no-op restart-wise for running pods until the next rollout).

DNS: the routers are independent of the failed cell. Only if the primary region's router tier itself is lost does
Route 53 switch `api.<region>` to the secondary routers (3 x 10 s health checks + 60 s TTL, inside the same budget).

RPO measurement: `tools/gameday/rpo_probe.py check` (last acknowledged sequence of the probe tenant vs. the last one
present after promotion, [section 8.4](#84-rpo-probe-tenant)); Aurora `AuroraGlobalDBReplicationLag` at T0; MSK
Replicator `ReplicationLatency` / message lag at T0.

### Planned (region evacuation, RPO 0)

1. Freeze the cell's writes: `POST /cells/{euw1c01}/read-only` (writes 503 + Retry-After, reads served).
2. Wait for outbox relays to drain and MSK Replicator lag 0; S3 CRR pending operations 0.
3. `aws rds switchover-global-cluster --global-cluster-identifier meridian-eu1 --target-db-cluster-identifier <euw2 arn>`
   (waits for full sync: RPO 0).
4. `POST /cells/{euw1c01}/offline`, `POST /cells/{euw2c01}/online`: euw2c01's services promote themselves in place;
   demote euw1c01's services (`POST /v1/internal/ops/cell-role/demote` on each, or `helm upgrade` to `role=standby`).
5. Make the roles permanent in Git (`deploy/` values: euw2c01 `role: primary`, euw1c01 `role: standby`).
6. Verify, then failback later the same way in reverse.

### Failback

Rebuild the old primary as the new secondary (the global cluster re-adds it), let S3 CRR (both ways) and a reverse MSK
Replicator catch up, then run the planned procedure in reverse.

## 6. Deployment models

| Model | Cell | Isolation | Operations |
|---|---|---|---|
| **Shared multi-tenant cell** (`SHARED`, default) | up to `capacity_tenants` (200) tenants; template provisioning places on the least loaded ACTIVE shared cell | per-tenant RLS in every database, tenant claim in every token, per-tenant keys where the domain needs them | Meridian operates; paired standby cell per shared cell |
| **Dedicated cell** (`DEDICATED`) | exactly one tenant (large bank, regulator demand): own EKS, Aurora, MSK, S3, KMS key, optionally own region pair | infrastructure-level | Meridian operates, same chart and modules; move in from a shared cell with a tenant move (`LOGICAL_REPLICATION`) |
| **Self-hosted package** (`SELF_HOSTED`) | the customer runs `infra/helm/meridian` (+ optionally `infra/tofu/modules/cell` / `region`, or their own Kubernetes, PostgreSQL 17+, Kafka 3.9+) in their data centre or cloud account | customer boundary; no Meridian access to data | customer operates with signed images and this runbook; registered in the registry only if Meridian routes to it (its `gateway_url` reachable by the router), otherwise standalone with its own tenant-service |

All models run the same images, chart and contracts; `global.cell.id` / `region` / `role` name the cell in telemetry
(`meridian.cell`, `cloud.region` resource attributes) and in the registry.

## 8. Game-day kit (MR-GAME-DAY)

### 8.1 Data mover

**Choice: a new platform app (`platform/data-mover`), not a mode of archive-service.** archive-service is a
tenant-scoped, spec-driven domain service in every cell with its own retention domain and WORM store; the mover is a
platform-operator, cross-cell process: it reads the source cell and writes the target cell at the same time (reach
into both, credentials for both buckets), keeps running while a cell is frozen or degraded, scales and fails
independently of any cell, and holds platform-wide authority (`platform:operator`, every service's data). Putting
that into archive-service would widen the blast radius and the privileges of a tenant-facing service. The mover is
deployed regionally next to the cell router (router chart, `dataMover.*`, off by default) with its own small progress
database (`mover_db`; locally `python tools/dev.py up data-mover`).

**Copy method: service-level export / import over the data-lifecycle API** (not logical replication). On the local
stack (one PostgreSQL, Flyway-managed schemas) and on Aurora (logical replication cannot filter one tenant's rows
across ~65 databases without per-tenant publications and slot management) the feasible approach is to let each
service export and import its own tenant rows:

- `POST /v1/internal/data-lifecycle/move/tables` - the tenant's tables of the service (every table with `id` and
  `tenant_id`; outbox, idempotency keys, nonces excluded), parents first (foreign keys), row counts, append-only flag,
  Flyway schema version (source and target must match);
- `POST /v1/internal/data-lifecycle/move/extract` - a page of the tenant's rows in id order, every column, under RLS
  and an explicit `tenant_id` predicate;
- `POST /v1/internal/data-lifecycle/move/import` - bulk `insert ... select from json_populate_recordset ... on conflict
  do nothing` (idempotent: a resumed page inserts nothing twice and never overwrites; RLS checks every row's tenant);
  rows whose parent arrives later (self-references to a later id) are inserted one by one where possible and returned
  as `deferred`, retried at the end of the service.

All three are reserved to the `data-mover` identity (`meridian.data-lifecycle.move-callers`, Keycloak client
`svc-data-mover` with `platform:operator`) and never routed by the edge gateway.

Run (state machine in `move_run` / `move_item`, lease per instance, any instance resumes after a crash, redelivered
events are no-ops):

1. **PENDING** until `not_before_checkpoint` (freeze + grace).
2. **COPYING**: plan (refuses a target that already holds rows of the tenant, or a schema drift), page every table
   (`page-size` 1000, throttle `rows-per-second` 5000 per instance), then the documents: `ListObjectsV2` of
   `<tenant>/` in the source bucket, GET + PUT of objects missing or different in the target (ETag / size), throttle
   `objects-per-second`. Document rows' `storage_uri` is rewritten to the target bucket (`meridian.mover.rewrites`).
3. **VERIFYING**: re-reads both cells: per table row count and SHA-256 over the canonical JSON of every row (sorted
   keys; rewrites applied to the source side); document listings (key, size, ETag). Any difference fails the run.
4. **CONFIRMING**: `POST /v1/platform/tenant-moves/{id}/confirm-copy` with the checkpoint and `verified=true`
   (Idempotency-Key `data-mover:confirm:<move>`); a `freeze_grace_pending` answer is retried 10 s later.
5. **COMPLETED**, or **FAILED** (operator: `/actuator/moves/{move}` on the management port shows per-table progress
   and digests; a `POST` there retries after the cause is fixed), or **CANCELLED** (`platform.tenant_move.cancelled`).

Evidence: `TenantMoverIT` (two PostgreSQL databases as two cells with the generated ledger and document schemas, RLS
on, the real move API, in-memory S3): only the moving tenant is copied, FK order incl. a deferred self-reference,
append-only tables, exact decimals, document copy and URI rewrite, resume after an injected 503 without duplicates,
freeze-grace retry, checkpoint format, redelivery no-op, non-empty target refused, a target changed after the copy
fails verification.

### 8.2 Standby promotion without restart

`meridian.cell.role` (`MERIDIAN_CELL_ROLE`) is a runtime switch (`CellRole`, libs/meridian-common). In a standby cell
`StandbyGate` (libs/meridian-events, a lifecycle bean that runs just before the Kafka listener registry) switches
`autoStartup` off on every listener container that would have started - including listeners with their own
`autoStartup` expression (approvals, audit), which the old `SPRING_KAFKA_LISTENER_AUTO_STARTUP=false` did not stop -
and the outbox relay starts paused. Promotion, on a background thread: wait until the database accepts writes
(`pg_is_in_recovery() = false`, `transaction_read_only = off`, up to `global.cell.promotion.dbWait`), replay the last
`replayOnPromote` of relayed events, resume the relay, start exactly the held containers. Triggers:

- **registry watcher** (default): while standby every service polls `GET /v1/platform/cells` (its own client, scope
  `platform:routing-read`) every 5 s and promotes itself when its cell's row is ACTIVE - the operator's
  `POST /cells/{id}/online`, the same action that publishes `platform.cell.status_changed`. Kafka cannot carry the
  signal: a standby cell's listeners are off by design. `global.cell.promotion.registryUrl` points a standby cell at
  the control-plane tenant-service.
- **operator endpoint**: `POST /v1/internal/ops/cell-role/promote {reason}` on each service (`/demote` for failback,
  `/retry` after a failed promotion, `GET /v1/internal/ops/cell-role` for the state); internal service tokens of
  `meridian.ops.callers` only (default `platform-ops` - Keycloak client `svc-platform-ops`, used by `tools/gameday` -
  and `tenant-service`). `python tools/gameday/faults.py promote-cell` / `cell-role` drive and watch all services.

Evidence: `StandbyGateTest`, `CellOpsControllerTest`. RTO impact: section 5 (no rolling restart on the critical
path, ~60-90 s of margin regained).

### 8.3 Outbox replay retention

`outbox.published_at` (generated DDL; partial indexes for pending and published rows): the relay stamps instead of
deleting while `meridian.events.retention.window` > 0 (default 72 h; 0 = old behaviour). `OutboxRetention` purges
relayed rows past the window in batches (every 15 min; never pending rows; skipped while standby).
`POST /v1/internal/ops/outbox/replay {from, to, basis: CREATED|PUBLISHED, event_types: ["payments.*", ...],
tenant_id, dry_run, max_events, reason}` re-publishes with the original `ce_id`, `ce_time`, key and payload plus the
extension `ce_meridianreplay`; replayed rows are stamped (`headers.replayed_at`, `replay_id`); throttled
(`meridian.events.replay.max-per-second`, 2000). `faults.py outbox-replay` fans it out over services. Metrics:
`meridian.outbox.replayed`, `meridian.outbox.purged`, `meridian.outbox.relay.paused`. Data protection: event payloads
stay in the service database for the window (same database and access as before; DSAR erasure does not rewrite
outbox rows - they age out within 72 h). Evidence: `OutboxRetentionReplayIT` (PostgreSQL 18, generated DDL).

### 8.4 RPO probe tenant

`tools/gameday/rpo_probe.py`: `setup` creates a probe ledger (tier 0) for a synthetic tenant; `write` posts one
balanced 0.01 journal entry at a time (`reference rpo:<run>:<seq>`, one Idempotency-Key per seq) through the router /
gateway and journals every acknowledgement locally; `check` (after the failover, against the promoted side) binary
searches the last sequence present and reports last acknowledged vs last present, lost writes, RPO in seconds, holes,
and the client-observed unavailability (RTO). Locally: `python tools/dev.py up tenant-service ledger-service gateway`,
then `rpo_probe.py setup`, `write`, `faults.py db-outage --execute`, `check`. Self-test without a stack:
`python -m unittest tools/gameday/test_rpo_probe.py`.

### 8.5 Fault injection

`tools/gameday/faults.py` prints (default) or runs (`--execute`, with `--cloud` for the cloud form) each fault with
the alerts it must raise and what to watch: `kill-service`, `db-outage` (local: stop `meridian-postgres`),
`db-failover` (Aurora `failover-db-cluster`), `region-failover` (Aurora Global `failover-global-cluster
--allow-data-loss`, or `--planned` switchover), `kafka-loss` (local: stop `meridian-kafka`), `kafka-broker` (MSK
`reboot-broker`), `cell-offline` / `cell-online` (registry). AWS FIS experiment templates:
`tools/gameday/fis/az-loss.json` (AZ subnets cut + Aurora failover), `region-loss.json` (every subnet of the primary
cell). Dashboard `Meridian / Game day (failover timeline)`; alerts `MeridianDataMoverRunFailed`,
`MeridianOutboxRelayPausedLong` plus the existing J6 / saturation alerts listed per fault.
