# Penetration test scope and rules of engagement (S22)

Last reviewed: 2026-10-07 · Owner: TBD (Security lead) · Test window: TBD · Tester: TBD (CREST / PCI-qualified
firm, independent of the development team) · Status: not yet performed (GAP-25)

Goal: independent assurance for GA, SOC 2 (CC4.1 / CC7.1), ISO 27001 (8.29, 5.35) and PCI DSS 11.4 (including
segmentation testing of the CDE). The test must confirm the fixes recorded in
[SECURITY_REVIEW.md - Remediation status](../SECURITY_REVIEW.md#remediation-status) and probe the residual risks
listed there.

## 1. In scope

| Area | Targets | Notes |
|---|---|---|
| Public API | Cell router `https://api.<region>.<staging domain>` -> edge gateway -> all `/v1/*` routes (`generated/routes.json`, bundled contract `/openapi.yaml`) | Both jwt mode (default) and the header policy (SEC-13 / SEC-16) |
| Channel APIs | `/v1/me` (customer-channel), `/v1/agent`, `/v1/business` (incl. M2M), `/v1/merchant` | Object-level authorization and step-up are the main focus |
| Provider callbacks | All `[public]` operations: rail inbound (`/v1/payment-rails/{id}/inbound`), 3DS `/authenticate`, token `/network/provision-requests`, card bureau, KYC, loan-origination bureau / e-sign, document e-sign, channel gateway, interop, notification delivery receipts | Signatures v2 and legacy flag both ON and OFF |
| Web apps | `web/customer-web`, `web/agent-app` (PWA incl. offline outbox and device keys), `web/business-portal`, `web/merchant-app`, `web/meridian-console`, `web/developer-portal` | Client-side storage, CSP / framing (SEC-22), token handling |
| Identity | Keycloak realm generated by `tools/keycloak_realm.py` (clients, scopes, mappers, step-up), identity-service (MFA, elevation, sessions) | Production IdP configuration if different |
| Card data environment | card-vault, card-authorization, card-tokenization, card-threeds, card-service; segmentation from all other pods | PCI 11.4.5 segmentation test |
| Infrastructure | Staging cell from `infra/tofu/envs/staging-eu1a` (EKS, Aurora, MSK, S3, KMS), Helm releases `infra/helm/meridian` and `meridian-router` | Authenticated cloud configuration review (read-only IAM role) |
| Internal (assumed breach) | A pod shell in a non-CDE service namespace (e.g. rewards-service) with its environment | Lateral movement, service-client abuse (GAP-16), Kafka produce, DB owner creds (GAP-22) |

Out of scope: AWS-managed control planes, third-party providers' systems (rails, schemes, KYC vendors), production
data, denial-of-service beyond the agreed rate tests, social engineering and physical tests (unless contracted
separately), SELF_HOSTED customer installations.

| Environment | Use | Data |

start otherwise), `global.trustedProxies` set, `platformOperatorTenant` set, IdP events enabled for the test window,
log capture for the test window (GAP-06 workaround: export pod logs daily).

Create users in the IdP and set admin-only attributes as described in the README channel sections.

## 4. Rules of engagement

- Written authorisation signed by Meridian (and by each tenant bank if any real tenant shares staging - it must not).
- Testing hours: TBD; emergency stop contact: on-call IC (see [RUNBOOKS.md](../operations/RUNBOOKS.md#13-incident-severity-matrix-and-on-call)).
- Source IPs declared in advance; testers identify traffic with header `X-Pentest-Id: <engagement id>` (not trusted
  for anything).
- No destructive actions against shared infrastructure (no deleting Aurora clusters, KMS keys, buckets); data
  modification only inside the pen-test tenants.
- Rate / load tests limited to agreed windows and volumes (e.g. 200 rps for 5 minutes per endpoint family).
- Critical findings (cross-tenant access, money creation, card data exposure, auth bypass) are reported **within 24
  hours** by phone + secure message, not only in the final report.
- Credentials and any card data observed stay inside the engagement; synthetic PANs only (test BINs).
- White-box: testers get this repository (read-only), the threat model and the security review; the team answers
  questions within one business day.

## 5. Priority attack scenarios

| # | Scenario | What to try | Expected control / evidence |
|---|---|---|---|
| P1 | **BOLA across channels** | Swap ids of accounts, cards, payments, payees, statements, documents, threads, outlets, tills, float requests, business payments, mandates, virtual accounts, stores, refunds, payout changes - T1 users referencing T1 objects of other customers / businesses / merchants / agents / stores, and T2 objects | 404, `*_action` row + `channels.*_action.denied` event; never 403 vs 404 oracle differences |
| P2 | **Tenant breakout** | Cross-tenant ids on every operator API; `X-Tenant-Id` / `X-User` / channel headers through router and gateway; tokens with `tenant_id` of T2; callbacks with `tenant_id` of T2; tenant registry reads; search; analytics saved queries; exports | RLS (`TenantFilter`, header stripping, SEC-13 / SEC-15) |
| P3 | **Approval bypass** | Self-approval; approval by a second account of the same person; creating approval requests for service-owned types as a user; omitting amounts; replaying decisions; changing the resource after submission (checksum / row_version); business matrix (split payments across bands, change matrix while pending, M2M approving); merchant refund cumulative cap; JIT elevation abuse (duration, role) | SEC-03 / SEC-20 / SEC-21 controls, `FourEyes`, `privileged_change` |
| P4 | **Replay and forgery of callbacks** | Replay v2 callbacks (nonce), skew outside 5 min, legacy body-only signatures with the flag ON vs OFF, cross-rail secret reuse, tenant swap in `tenant_id`, pacs.008 crediting arbitrary accounts, pacs.002 status forging, 3DS result without CAVV binding | `CallbackVerifier`, nonce store, SEC-17; legacy flag residual (GAP-15) |
| P5 | **SSRF** | Webhook endpoints, `/test` deliveries, file-gateway `content_url`, KYC provider `base_url`, rail `endpoint_url`, card program `jit_webhook_url`, tenant SMTP host, sanctions `source_url`; DNS rebinding, redirects, IPv6 / IPv4-mapped, decimal IPs, `169.254.169.254`, `kubernetes.default.svc` | `OutboundUrlPolicy` (SEC-08/09/18/39) |
| P6 | **Idempotency abuse** | Reuse a key across resources, users and methods; replay with modified bodies; concurrent first use; keys older than 10 min (stale claims); predictable derived keys in channels | 422 `idempotency_key_reused`, SEC-19 / SEC-34 |
| P7 | **Money races** | Parallel reversals, returns, refunds, wallet reversals, FX quote accepts, inbound duplicates, card authorisations against limits (counters read without lock - known), business payment release retries, agent cash-out confirmation | SEC-04..07, SEC-28; card limit counters known gap ([SPEC_BACKLOG Cards](../SPEC_BACKLOG.md#wave-b-results-and-open-items)) |
| P8 | Card data | Vault reveal without step-up, with old `auth_time`, with portal / agent tokens; `lookup` / `verify` from user tokens; CVV2 brute force (try limit 5); PIN try counter; key rotation as non-admin; segmentation from every non-CDE pod | SEC-11 / SEC-24; GAP-02 |
| P9 | Step-up bypass | Password-grant tokens (no `auth_time`) on step-up routes; stale device proofs; `acr` manipulation; agent device proof replay | 401 `step_up_required` |
| P10 | Assumed breach | From a non-CDE pod: call other services with the shared service client, set `X-Meridian-Service` to an owning service, produce forged events to `meridian.platform.v1` (approval decisions), connect to Aurora with the mounted owner credentials | Expected to **succeed** today (GAP-16, GAP-22): document impact |
| P11 | Offline agent device | Extract IndexedDB outbox, brute-force PIN, replay signed batches to another agent, tamper ordering | SEC-23 residual, device signature checks |
| P12 | Web apps | XSS, clickjacking, open redirects on callback routes, token leakage via Referer, service worker caching of `/v1` | SEC-22, PKCE / state checks |
| P13 | Resource exhaustion | Oversized bodies, ReDoS through tenant regexes, OTP / SMS pumping, export 10k-row caps | SEC-16 / SEC-26 / SEC-30 |

## 6. Reporting and retest

1. Daily stand-up with the tester; criticals within 24 h (section 4).
2. Draft report within 10 business days: executive summary, methodology, findings with CVSS 4.0 and a banking impact
   rating (money integrity, card data, tenant isolation, PII), reproduction steps, evidence, remediation advice.
3. Findings are imported into `docs/SECURITY_REVIEW.md` style tracking (new ids `PT-nn`) with status, fix, regression
   test and residual risk; each fix needs an automated regression test before closure.
4. Remediation SLAs: Critical 7 days, High 30 days, Medium 90 days, Low next release (TBD by risk committee).
5. Retest of all Critical / High within the engagement (free retest window 30-60 days); letter of attestation for
   customers / auditors after retest.
6. PCI: segmentation test result recorded separately (11.4.5, every 6 months for service providers).
